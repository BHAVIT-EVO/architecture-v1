# UI-IA-0002 — Evo Desktop: Proposed Information Architecture and Screen Design

**Status:** Proposal for approval. Nothing here is implemented. No code has been written.
**Depends on:** `UI-REVIEW-0001.md` (current-state review and defect register).
**Scope:** UI information architecture, visual design, egui implementation.
**Frozen and untouched:** product model, architecture, backend contracts, RFCs, IS documents.
**Date:** 2026-08-16

---

## 1. The thesis, in one page

Evo's UI has one job that no other job may crowd out: **make a person recognise where they were, and let them press one thing.**

Recognition, not reconstruction. That distinction drives every decision below. A screen the user has to *read* has already failed; a screen they *recognise* has succeeded. Reading is linear and slow. Recognition is instant and pre-verbal — it comes from position, size, material, and one sentence in the user's own words.

So the design has exactly one rule, and everything else is derived from it:

> **Each level of the product states one fact, in one voice, on one surface — and defers everything else.**

The current UI's failure is not ugliness. It is *simultaneity*: fifteen informational blocks presented at once, at comparable weight, on identical surfaces, so nothing can be recognised and everything must be read (`UI-REVIEW-0001.md` §6.3). The fix is not prettier cards. It is deciding, at each level, which single fact earns the surface — and then having the discipline to put the other fourteen things behind disclosure, or delete them.

Three commitments follow, and they are the whole proposal:

**One dominant fact per level.** Home: the work you said you're continuing. Workspace: where you left off. Continuation: what you're continuing across. Continue: what actually happened. Each is one sentence, largest on its screen.

**One control per question.** The user has one question — *what am I continuing?* — so they get one control. Not a "Mark to continue" button in one column and a checkbox list in another (`UI-REVIEW-0001.md` §5.2). §3 shows how one control drives two canonical writes without changing either.

**One surface for what matters.** At most one elevated white surface per screen. Everything secondary lives as text directly on the window material. This is V3 §12's own stated requirement — *"Before reading a word, the user should understand: white elevated thing = my work; translucent material with quieter text = context"* — and it is the single largest visual correction available.

## 2. Proposed information architecture (Deliverable 6)

### 2.1 The four levels

```
┌─ HOME ───────────────────────────────────────────────────────┐
│  Q: What work can I continue?                                 │
│  ONE FACT: the body of work you told Evo you're continuing     │
│  (absent when you haven't told it — then no emphasis at all)   │
│  REST: a quiet list of other bodies of work. No ranking.       │
└──────────────────────────┬────────────────────────────────────┘
                           │ open one
┌─ WORKSPACE ──────────────▼────────────────────────────────────┐
│  Q: What is this body of work, and where was I?                │
│  ONE FACT: "You left off in {resource}."                       │
│  REST: one line of provenance. History behind disclosure.      │
└──────────────────────────┬────────────────────────────────────┘
                           │ same screen, below the fact
┌─ CONTINUATION ───────────▼────────────────────────────────────┐
│  Q: Is Evo right about what I'm continuing?                    │
│  ONE CONTROL: one list, one set of marks, one commit           │
│  HONESTY: each marked resource shows whether it can be reopened │
└──────────────────────────┬────────────────────────────────────┘
                           │ press Continue
┌─ CONTINUE ───────────────▼────────────────────────────────────┐
│  Q: What actually happened?                                    │
│  ONE FACT: per-resource outcome, including honest failures      │
│  PERSISTS until dismissed. Never erased by background capture.  │
└───────────────────────────────────────────────────────────────┘
```

Two destinations remain (Home, Workspace) with Settings as a modal. Levels 2, 3 and 4 are regions of the Workspace screen, not separate screens — because they are one continuous thought and splitting them would cost presses, and presses are Time To Productive.

### 2.2 The three sets, given three visual languages

`UI-REVIEW-0001.md` §5.1 showed the current screen rendering membership, declared continuation, and executable targets with one affordance and one material. The proposal gives each its own language, so the distinction is visible before it is read:

| Set | Material | Affordance | Preflight shown? | Copy |
|---|---|---|---|---|
| **Where you left off** (resume point) | M2 elevated, largest type | none — read only | no | "You left off in {resource}." |
| **What you're continuing** (declared + draft) | M2 elevated, same surface | checkmark, toggleable | **yes, always** | "What you're continuing" |
| **Everything else in this work** (membership) | M0, receded text, behind disclosure | **no checkmark at rest** — an explicit "Add" action | not until added | "Everything else Evo has seen in this work ({n})" |

The critical change is the third row. Today a historical member carries the same checkbox as a declared member but **no preflight dot**, so the user discovers a resource cannot be reopened only *after* committing to it — the product's honesty posture inverted at the exact moment of commitment. In the proposal, promoting a historical resource is an explicit act that *moves it into the control above*, where it immediately acquires a preflight status as an uncommitted draft. Honesty arrives before commitment, which is the only ordering consistent with Law V and Law IX.

### 2.3 What each level is allowed to emphasise

Because recency is not authority and ranking is prohibited, "what may be emphasised" is a real constraint, not a style question.

**Home may emphasise exactly one thing: the workspace containing the user's current designation.** This is legitimate because it is *the user's own statement*, not Evo's inference — derived deterministically from canonical evidence, ranking nothing. `state::select_workspace_with_designation` already computes it and already justifies it in its own doc comment against RFC-0011 and RFC-0006 — and `state.rs:107` already calls it on every reload. `app.rs` then overwrites the result from `self.selected` and never reads the original, so today the hero's identity is derived and discarded rather than displayed (`UI-REVIEW-0001.md` D-38). Building the hero is closer to *stopping a deletion* than to adding a feature.

RFC-0010 settles the question of whether that is permissible, and it is worth quoting because the answer is easy to get wrong. Its prohibited-evidence list bars recency, frequency, focus, titles, membership, importance and confidence — but every one of those is a signal *Evo* would be interpreting. Its Open Question 2 asks separately "whether a witnessed work-state fact may ever be user-directed (a request to continue)", noting that at the time of writing "user requests have no canonical representation in the current architecture." RFC-0011 and RFC-0013 are the milestone that answered that question yes. So a designation is not a ranking that slipped past the prohibition; it is the category the prohibition was explicitly leaving room for. The hero surfaces what the user said, which is the one thing Home is allowed to elevate.

**When there is no designation, Home emphasises nothing.** No hero, no top card, no "most recent." Just the heading and the list. This is Law VI in layout form: silence rather than fabrication. It also means the hero is *earned* — its presence is itself information ("you told Evo where you're working"), and its absence is honest.

**Ordering of the list remains the workspace log's append order** — stable, non-ranking, already what happens. With two new prohibitions made explicit in code comments so they are not lost: the UI must never label this order (no "Recent"), and must never let position imply priority (no numbering, no size variation down the list).

## 3. The central change: one control, two writes (requires your approval)

This is the largest proposal in the document and the one I most want you to interrogate.

### 3.1 The problem restated

The backend has two continuation writes with different arity: designation is single-subject (RFC-0011); a continuation surface requires ≥2 subjects (RFC-0013). The current UI exposes them as two separate controls, in two columns, with two vocabularies, two commit styles, and two status lines — for what the user experiences as one question. And the brief forbids the user ever learning the words "designation" or "continuation surface."

### 3.2 The proposal: arity-dispatched commit

**One list. One set of marks. One button. The UI chooses the correct canonical write from what the user marked.**

```
What you're continuing
─────────────────────────────────────────────
  ✓  investor-deck.key            can reopen
  ✓  term-sheet-notes.md          can reopen
  ✓  pitch-notes                  can't reopen ▾
  ☐  appendix.numbers

  [ Save what you're continuing ]
─────────────────────────────────────────────

marks = 1   →  write OBS-WORK-DESIGNATED
marks ≥ 2   →  write OBS-CONTINUATION-SURFACE
marks = 0   →  button inactive: "Mark at least one thing you're continuing."
```

### 3.3 Why this does not change semantics

It creates no new canonical state and invents no concept. It selects between two writes that already exist, based on what the user actually said. If a person marks one resource, "this is the work to continue" is the semantically correct canonical statement — that is precisely what a designation is. If they mark three, "my work continues across these" is correct — that is precisely a surface. Rule 18 is satisfied: the UI is not manufacturing state, it is routing an intent to the write that expresses it.

What it buys:

- The forbidden vocabulary disappears entirely from the interface.
- RFC-0013's ≥2 constraint stops being a trap. Today, unticking to one resource produces a rejection for an unstated rule (`UI-REVIEW-0001.md` D-10). Under the proposal, one mark is simply *legal*, because it routes to designation.
- Two status lines, two commit styles and two mental models collapse to one.
- Draft-versus-committed becomes the only state distinction the user must perceive, and V4 already specifies exactly how to show it (committed: accent fill; draft: 20% accent fill).

### 3.4 The two consequences you need to weigh

**(a) It depends on BE-01 being fixed first.** `handle_designation` persists via `new_with_designated`, which passes `continuation_surface: None` — so writing a designation currently *erases* a declared surface. Under arity dispatch, a user going from three marks down to one would silently destroy their surface. **The merged control must not ship before BE-01 is fixed.** Until then the honest interim is to refuse the transition rather than perform it silently — and refusing is itself worse than the fix, which is why I would sequence BE-01 ahead of Phase 2 (§10).

**(b) The two writes have different scope, and the merge makes that visible rather than hiding it.** A designation is global; a surface is per-workspace-intersected. So marking exactly one resource in workspace A makes a *global* statement. I propose treating that not as a leak but as **the mechanism behind Home's hero**: the workspace you designated is the one Home emphasises. The user never learns the word, but they see and understand the consequence — *"I told Evo I'm working on this, so it's the first thing I see."*

That is the cleanest available answer to "what may Home emphasise?" But it does couple two levels of the product, and if you would rather Home never emphasise anything, the merge still works and Home simply loses its hero. **This is the decision I need from you.**

## 4. Navigation model (Deliverable 8)

### 4.1 Topology

Unchanged, because it is already right: two destinations derived from `Option<WorkspaceId>`, plus one modal. No tabs, no breadcrumbs, no third surface, no command palette.

```
FIRST RUN (1→2→3, skippable after step 1)
      │
      ▼
    HOME ⇄ WORKSPACE          Settings: modal from either
      │        │
      └────────┴──► Continue (executes; report appears in the Workspace bar)
```

### 4.2 Chrome that never scrolls

The single biggest navigational fix. Today the back control and the capture banner live *inside* the scroll area, so the way out of a screen and the disclosure that Evo is not capturing both scroll away (`UI-REVIEW-0001.md` D-14).

Proposed fixed regions, top to bottom: a header (52px — wordmark, back control on Workspace, Settings) that never scrolls; a banner slot below it, present only when capture is degraded, also fixed; then the scrolling body; then the pinned action bar. Only the body scrolls. Ever.

### 4.3 Continue from Home

The hero carries the plan sentence and a Continue button. Pressing it executes and navigates into that workspace, so the report appears where reports live. This is one press from launch to productive, which is the entire metric — and it costs no honesty, because the plan sentence states what will be attempted and the report states what happened. Execution still routes through `state::run_execution` and the existing execution boundary; Rule 16 is untouched.

### 4.4 Keyboard model

Currently there is none (`UI-REVIEW-0001.md` D-02), and V4 §9 requires full reachability. Proposed:

| Key | Home | Workspace |
|---|---|---|
| `Tab` / `⇧Tab` | search → chips → hero → cards | back → marks → disclosure → commit → Continue |
| `↑` `↓` | move through cards | move through marks |
| `Return` | open focused card | toggle focused mark |
| `Space` | — | toggle focused mark |
| `⌘Return` | Continue the hero | Continue |
| `Esc` | clear search, else nothing | close sheet, else back to Home |
| `⌘,` | Settings | Settings |
| `⌘F` | focus search | — |

Every interactive element becomes `Sense::click().union(Sense::focusable())` with a visible focus ring — a 2px accent outline at the element's own radius. Focus ring is the one new visual element the proposal introduces.

## 5. Interaction model (Deliverable 9)

### 5.1 Draft, commit, and who owns transient state

The correction flow is draft-then-commit, and the draft belongs to the *user's editing session* — not to the reload cycle. Concretely: a single owned struct holding the mark set, the disclosure state, the last commit status, and the execution report, cleared only by an explicit user act (commit, dismiss, navigate away) and **never** by a canonical reload. This is what fixes B-01 and B-02 at the root rather than patching symptoms.

The rule to encode: *canonical reloads may replace derived state; they may never touch user-authored transient state.*

### 5.2 What appears only contextually

The current screen never simplifies (`UI-REVIEW-0001.md` §6.3). Proposed appearance conditions:

| Element | Appears only when |
|---|---|
| Commit button | the mark set differs from what is committed |
| "You've changed what you're continuing" | same |
| Preflight reason text | the resource is not READY **and** the user discloses it |
| "Everything else in this work (n)" | n ≥ 1 |
| Capture banner | capture is degraded or permission missing |
| Cross-workspace note | the designated resource is not a member of *this* workspace |
| Execution report | the user pressed Continue and has not dismissed it |
| Home hero | a designation exists and resolves to a workspace |
| Provenance line | always — but as one sentence, not a grid |

And what is **deleted outright**: the "Blocked by" section (can never populate — `blockers` is always empty), the fifty-row snapshot history, the duplicated identity metadata, the second Home click target, the always-on instructional sentence.

### 5.3 Disclosure, not density

Preflight reasons become disclosed rather than always-visible — which is a *restoration* of V3 §6.8's specified behaviour ("Click: 'Can't reopen this — ' + reason"), not a departure from it. A resource that can be reopened says three words and stops. A resource that cannot says three words and offers `▾`. The verbatim canonical reason string appears on disclosure, unmodified.

### 5.4 Motion

V4 §6.9 timings adopted as specified, with nothing added: press feedback instant; bar expand 200ms ease-out; collapse 150ms; per-target fade 120ms per line. One animation clock, one id, computed once (fixing B-04). Nothing else in the product moves. Stillness at rest is a spatial quality and also an honesty quality — a UI that animates while asserting facts looks like it is persuading.

### 5.5 Latency states that currently cannot exist

Because derivation is synchronous in `new()` and execution blocks the frame, the product has no loading state and no executing state (`UI-REVIEW-0001.md` D-31, D-34). Proposed:

- **Loading** — first-launch replay moves to a worker. The window appears immediately with the heading and *"Evo is reading its record of your work."* No spinner, no progress bar: progress is unknowable and a fake bar would be a confidence claim.
- **Executing** — V4 §7.17, finally implementable. The bar expands on press and each target resolves in place as it completes. This is also the honest presentation of a slow AX call: the user sees which resource is being worked on.
- **Preflight staleness** — probing moves off-thread. Because a probe result is a statement about the recent past (invariant 24), the copy changes from *"will be attempted"* to *"As of a moment ago, 3 of 5 could be reopened. Evo checks again when you press Continue."* Strictly more honest, and it removes the product's one over-promise (D-24).

## 6. Visual system (Deliverable 10)

### 6.1 The one change that matters: make the materials actually different

`UI-REVIEW-0001.md` §6.2 showed all three card helpers are the same surface. The proposal gives M0–M4 real, distinguishable treatments, and — critically — **limits how many M2 surfaces may exist.**

| Material | Treatment | Border | Shadow | Where |
|---|---|---|---|---|
| **M0** window | `#E8E5E0` (Tier 2), or genuinely translucent if Tier 2/3 is pursued | — | never | window; secondary content sits as text directly here |
| **M1** content well | `#F4F1ED` (`surface_alt`, already defined) | — | never | search well, disclosure regions |
| **M2** elevated | `#FFFFFF` | **none** | `[0,2,16,α20]` | **at most one per screen** |
| **M3** action | near-white `α242` | 1px top hairline | real upward shadow via `action_bar_frame()` | pinned bar, primary buttons |
| **M4** transient | near-white | — | `[0,12,40,α41]` | Settings, as a true modal layer |

Two specific decisions inside that table do most of the perceptual work:

**Remove the hairline border from M2.** Shadow's job is elevation (V4 §6.6). A shadow *and* a border double the signal and produce the universal "dashboard card" read. Shadow alone reads as a surface; shadow plus border reads as a card. This single change moves the product further from SaaS than any other edit available.

**At most one M2 surface per screen.** Workspace Detail gets exactly one elevated surface, containing the resume point and the continuation control — because those are one thought. Provenance, history and related work become text on M0. Home's list entries are the exception that proves the rule: they are M2 because each *is* a distinct object placed in space, but the search well is M1 and the heading is text on M0.

**And the honest note about M0.** The Tier 2 approximation `#E8E5E0` is fine *provided the other four materials do their job*. What produced the current SaaS read was Tier 2 plus a collapsed hierarchy — an opaque page with identical white cards, which is exactly what V3 §1 was written to condemn. If Tier 2 remains (my recommendation for Phase 1), the design must not pretend otherwise, per V4 §8's instruction not to silently substitute. Genuine translucency via `with_transparent(true)` should be attempted as a separate, isolated experiment, and abandoned without regret if legibility suffers.

### 6.2 A closed type scale, enforced by the API

Seven roles exactly, as V4 §6.3 specifies. The enforcement mechanism matters more than the values: `theme` should expose **role functions that take no size argument** — `display()`, `display_small()`, `title()`, `body()`, `body_strong()`, `small()`, `tiny()`. Call sites then physically cannot invent 11.5 or 14.5, and D-08 cannot recur. Where the current code passes a size, that size is a design decision that leaked into layout code.

Weight comes from the real variable-font families `theme.rs` already registers. `.strong()` is banned outright — it only changes colour, which reads as a different tier rather than emphasis (D-26).

### 6.3 Accent discipline

Accent `#0A5E58` means exactly one thing: **you can act on this, or you have already acted.** Primary buttons, committed marks, focus rings. Nothing else.

The resume point sentence moves from 30pt accent teal to **30pt near-black `#1A1A1C`** (D-37). It is already the largest thing on screen; size is sufficient. Teal on a multi-line sentence makes a paragraph of saturated colour and destroys the accent's meaning by making it decorative.

### 6.4 Status presentation

One vocabulary, in the user's language, in one register — fixing the ALL-CAPS-versus-lower-case split (D-23):

| Backend | Before pressing | After pressing |
|---|---|---|
| Ready / Opened | "can reopen" | "opened" |
| Unavailable | "can't reopen" ▾ | "couldn't open" ▾ |
| Ambiguous | "needs clarifying" ▾ | "needed clarifying" ▾ |
| Unsupported | "Evo can't open this" ▾ | "Evo can't open this" ▾ |

Colour always paired with words (V4 §9, already honoured). Dots become **allocated** 6px circles — `allocate_exact_size` then paint at radius 3.0 — rather than 12px circles painted at a cursor offset (D-09). The verbatim canonical reason string appears on disclosure, unaltered.

### 6.5 Spacing and geometry

Tokens are already correct and stay. Three corrections: no off-system arithmetic at call sites (`PAGE_PAD - 12.0`, `GAP_ENTRY + 16.0` both disappear with the layouts that needed them); one content measure across both screens, so the product stops changing width (D-13); and real breakpoints that match the actual window — either apply `MIN_WINDOW_WIDTH = 420` in `main.rs` and design the narrow layout properly, or raise the split threshold well above the 680px minimum. The present 700-against-680 arrangement makes the stacked layout a 20px accident (D-28, D-36).

### 7.3 Home — search active

Search sits in an M1 well below the hero, so searching never displaces the one thing the user most likely wants. Chips inline. Matching remains `String::contains`, which is the honest whole of the search product today — so the placeholder states its scope: *"Find a body of work by name…"*, and the empty result says what was searched rather than implying more (D-18).

**No matches** — one sentence naming *both* active constraints when both are set, plus a single "Show everything" reset. Today a user filtered to *Commits · Today* who also typed cannot tell which constraint eliminated everything.

**Backend binding** — title from `state::workspace_card`; provenance from `attachments().len()`, `snapshots().len()` and `Snapshot::captured_at` (the only timestamps that exist); resume sentence from `RestorationPlan::resume_point` via `describe_artifact`; explanation rendered from the canonical reason string verbatim; `Next:` from `NextStep::description()`; marks from `RestorationSelection` ∪ draft; status from `preflight`.

**What disappears** — the `designation_card` as a separate control (merged, §3); the entire `witnessed_card` including fifty snapshot rows, replaced by the one provenance sentence (D-16); the duplicated identity metadata (D-15); the "Blocked by" branch (D-19); the always-on instructional sentence; the sidebar (§5.7 — the primary decision returns to the primary column).

**Contextual appearance** — commit button and its explanation only when the mark set differs from committed; reason text only on disclosure of a non-READY resource; the history line only when n ≥ 1; the cross-workspace note only when the designated resource is genuinely not a member here.

**Interaction** — marks toggle instantly into draft (20% accent fill) and never write on toggle. Committing writes once. A canonical reload replaces derived state and leaves the draft alone (fixing B-01).

**Insufficient-evidence variant** — the resume sentence is replaced by *"Evo remembers this body of work, but its record does not show which resource to continue from"* (existing copy, unchanged), followed by the candidate list *inside the same control* — so marking a candidate is the same gesture as editing continuation, not a second mechanism. This is the state invariant 23 says is the ordinary condition of a young workspace, so it must not read as failure: same surface, same weight, one different sentence.

**No-snapshot variant** — *"Evo remembers this work, but its continuation details are still being recorded."* One sentence on M2, nothing else, no empty control.

### 7.5 Continuation editing (a state of 7.4, not a screen)

```
   ✓  investor-deck.key           can reopen
   ✓  term-sheet-notes.md         can reopen
   ◐  appendix.numbers            can reopen        ← draft, 20% accent
   ☐  pitch-notes                 can't reopen  ▾

  You've changed what you're continuing.
                        [ Save what you're continuing ]
```

Three mark states, visually distinct: committed (accent fill, white check), draft (20% accent fill), unmarked (hairline). V4 §6.7 already specifies exactly this and the current implementation already renders it correctly — it is one of the better details in the code and survives unchanged.

**Arity behaviour** (§3.2) — one mark writes a designation; two or more write a surface; zero leaves the button inactive with *"Mark at least one thing you're continuing."* The user never sees either term.

**Rejection state** — V4 §7.25, currently unimplemented. If a write is rejected, the marks stay exactly as the user left them (never silently reverted) and one sentence states what happened. Reverting a user's edit on rejection would be the UI overriding the user's judgment, which Law IX forbids.

**Promotion from history** — disclosing "Everything else Evo has seen in this work" lists historical members as receded text on M0 with an explicit `+ Add` per row. Adding moves the row *up into the control* as a draft, where it immediately shows a preflight status. Honesty precedes commitment (§2.2).

### 7.6 Preflight (a property of rows, not a screen)

Preflight is never its own surface. Each row carries a 6px allocated dot and two or three words. Non-READY rows offer `▾`; disclosing shows the verbatim canonical reason on one indented line — real layout indentation, not two literal spaces inside the string (D-29).

The summary sentence beneath is the product's most honesty-critical line, and the proposal changes it: **"As of a moment ago, 2 of 3 could be reopened. Evo checks again when you press Continue."** This replaces *"will be attempted"*, which promises something preflight cannot promise (invariant 24, D-24). It is the only copy change I consider mandatory.

### 7.7 Continue — resting, executing, and reported

```
RESTING     │ Will reopen investor-deck.key and 1 more    [ Continue ] │

EXECUTING   │ Reopening…                                                │
            │   investor-deck.key                            opened     │
            │   term-sheet-notes.md                        opening…     │

REPORTED    │ 2 of 4 reopened.                                      ✕   │
            │   plan.md                                       opened    │
            │   research-tab                            couldn't open   │
            │     No browser window with this tab is open               │
            │   presentation.key                              opened    │
            │   slack-thread                    Evo can't open this      │
            │     Evo cannot open this kind of resource                  │
            │                                                            │
            │ One failure never hides a success.                         │
```

**Layout** — the plan sentence is laid out in a region that reserves the button's width *first*, so the label can never squeeze the product's only primary action (D-03). Expanded height is measured from laid-out content rather than computed as `64 + 24n`, which currently clips exactly the partial-restoration reasons `ARCHITECTURE.md` §9 requires (B-03).

**Persistence** — the report stays until the user dismisses it with `✕` or navigates away. It is never erased by a canonical reload. Today it deletes itself within about two seconds precisely *because* Continue succeeded — the windows it opened generate observations that change the signature (B-02). That is the single worst behaviour in the shell.

**Partial restoration** — the default presentation, not a variant. The heading counts plainly ("2 of 4 reopened"), every attempt is listed, every failure carries its verbatim reason, and no failure suppresses a success. There is no failure *screen*: a Continue where nothing opened is the same layout reporting four honest failures.

**Animation** — one clock, one id, computed once (fixing B-04): expand 200ms, collapse 150ms, per-target fade 120ms.

### 7.8 Empty states

**Home, nothing remembered** — existing copy retained verbatim; it is excellent. Centred on M0, no card, no illustration, no call to action, because waiting *is* the correct behaviour.

The one change: when capture is degraded or permission is missing, the empty screen must say so **in the empty state itself** rather than relying on a banner that scrolls. Today that match arm is literally empty (D-05), so in the exact case where emptiness is *caused* by missing permission, the screen offers no explanation:

> **Evo remembers nothing yet.**
> Evo can't tell which window you're working in until you grant Accessibility access — so it may not notice your work.
> [ Open System Settings ]  [ Check again ]

**Workspace with no snapshot** — §7.4 variant. **Search with no matches** — §7.3.

### 7.9 Permission and error states

**Permission** — one fixed banner in chrome (never scrolling), warning-coloured, with `Open System Settings` and `Check again`. Stated as a *capability* limit rather than a fault: Evo continues to record files, URLs and commits.

**Storage error** — the screen is honest and correctly headed, fixing the current `title("Current work", 16.0)` above "Evo could not read its stored state" (D-17):

> **Evo couldn't read its record.**
> What's shown below may be out of date. Evo will try again automatically.

Stale content renders at one uniform reduced opacity, replacing `0.6 - 0.2 * index.min(1)` which dims the first card to 0.6 and every other card to 0.4 for no reason (D-25). All stale data is equally stale.

**Loading** — new. Heading plus one sentence, no spinner, no progress bar: progress is unknowable and a fake bar is a confidence claim.

### 7.10 Settings

A true modal (`egui::Modal` or `Area` + `Order::Foreground` with input capture) over a dimmed M0 — fixing the current in-flow scope through which content behind stays clickable (D-11). Height driven by content, not hardcoded 428/380 (D-12).

Sections: capture status with permission actions when relevant; storage location with *"All data stays on this Mac"*; About with the local-only claim. `Esc` and `Done` both close; focus is trapped while open.

I would additionally surface the local-only claim somewhere more visible than Settings → About. It is currently stated in full once, during first run, at the moment of least investment, and then hidden. It is the product's strongest trust asset.

Its real audience is a developer debugging derivation, and the storage location is already exposed in Settings for exactly that purpose. If a debug view is wanted later it should be a debug view, not a card on the primary screen.

## 8. What should remain from V4 (Deliverable 11)

V4 and V3 are strong documents. Most of what is wrong with the shipped UI is *under*-implementation of them, not disagreement with them.

**The material concept M0–M4.** Correct, Apple-consistent, and the right vocabulary. It has simply never been implemented as five distinguishable materials (§6.1).

**Every token value.** Colours (`#1A1A1C` / `#58585D` / `#86868B` / `#AEAEB2`, accent `#0A5E58` and its states, the four status colours), the 4px spacing base and all derived gaps, radii (12/14/10/8), and the four shadow definitions. `theme.rs` already encodes these faithfully. No token needs changing except one candidate flagged for measurement (`RECEDED` on `BG` may sit below V3's own ≥3:1 floor).

**Seven type roles.** V4 §6.3 is right; the implementation drifted to ~13 sizes. §6.2 proposes enforcing the seven mechanically rather than restating them.

**The translucency rule and the no-stacking rule.** "Only M0 and M4 are genuinely translucent"; never stack translucent layers. Both correct and both worth keeping even under the Tier 2 approximation.

**Motion timings, exactly as specified.** 0ms press, 200ms expand, 150ms collapse, 120ms per line. Nothing added.

**Colour never used alone for status.** V4 §9. Already honoured; keep.

**6px preflight dots.** V4 §6.8 is right; the implementation renders 12px (D-09).

**Draft-versus-committed checkbox treatment.** V4 §6.7's accent fill versus 20% accent fill is exactly right and already correctly implemented — one of the best details in the code.

**Almost no iconography.** V3 §6.9's "words do the work" is not an aesthetic preference, it is forced by the data: bundle identity is deliberately discarded at capture, so there are no icons to show. The typographic identity is honest.

**The anti-pattern list.** V4 §10 / V3 §13 in full: no dashboard, no chatbot, no badges, no file browser, no relevance ranking, no command palette, no glassmorphism overload, no fake confidence, no hardcoded background pretending to be spatial.

**Tier honesty.** V4 §8's instruction not to silently replace Tier 3 requirements with hardcoded approximations. Worth restating: the current UI *did* substitute, and §6.1 explains why that substitution plus a collapsed hierarchy produced the SaaS read.

**The copy.** V3 §10 preserves existing copy verbatim; so do I, with the one mandatory exception at §7.6.

**The pinned bar, the two-destination navigation, and the golden path.** All correct.

## 9. What should change from V4 (Deliverable 12)

Stated as disagreements, with reasons, since you asked me not to assume a design is good because it exists.

**9.1 The two-column main/sidebar split should go.** The prototype's `col-main` / `col-side` structure became a layout in which the sidebar holds the declared continuation, the preflight status and the Declare action — the most consequential content in the product — while the wide column holds a restatement, a competing control and an audit log. That inverts the brief's own instruction that a sidebar "must never overpower the actual Workspace." One column, one elevated surface.

**9.2 Designation and continuation surface should not be two sections.** V3 §7.3 shows "Mark what you're continuing" and "Current continuation" as two sections in one surface — better than today's two columns, but still two mechanisms for one question, still two write paths, still the ≥2 trap. §3 proposes one control with arity-dispatched commit.

**9.3 The resume sentence should not be accent-coloured.** V4 §7 and V3 §7.3 both specify 30pt in `#0A5E58`. At display size across multiple lines this is a paragraph of saturated teal, and it destroys the accent's meaning as "you can act on this." Near-black at 30pt is already dominant (§6.3).

**9.4 M2 should not carry both a border and a shadow.** V4 §6.2 gives M2 a 1px `rgba(0,0,0,0.06)` border *and* §6.6 gives it a shadow. Doubling the elevation signal is what produces the card read. Shadow alone (§6.1).

**9.5 There should be at most one M2 surface per screen.** V4 §7.9's diagram already implies this, but its component inventory assigns M2 to the foreground zone, the workspace surfaces, the designation rows, the surface lists *and* the preflight dots — which in practice became four to five identical white rectangles. The constraint should be explicit and enforced.

**9.6 The 25-screen catalogue should collapse to ~14 real states.** Several V4 entries are the same code path with different data (7.4/7.5, 7.6/7.7, 7.23/7.8). Counting them separately hid the fact that four genuinely distinct states were never built (Executing, Rejection, preflight disclosure, and any loading state). A shorter, honest list is more useful than a longer aspirational one.

**9.7 Preflight reasons should be disclosed, not always visible.** V3 §6.8 already specifies disclosure; V4 §7.15 shows them inline; the implementation renders them always. Disclosure is the correct reading and a large part of the density fix.

**9.8 The witnessed/snapshot history should not be a screen region at all.** No V4 screen shows fifty rows, but the component inventory legitimises a "witnessed summary," which grew into an audit log. One provenance sentence (§7.4).

**9.9 The Home hero is new, and needs your approval.** V4's Home is a uniform list of M2 surfaces — faithful to "no ranking," but it leaves the product's front door with no dominant fact. §2.3 argues the designated workspace may be emphasised because it is the user's own statement rather than Evo's inference. This is the proposal's biggest addition to V4.

**9.10 Keyboard navigation must be actually built.** V4 §9 requires it and lists it under Tier 1 as "directly implementable." It does not exist at all (D-02). Not a disagreement — an unmet requirement worth naming as such.

## 11. Architectural matters I am flagging, not proposing (as instructed)

Per the brief: identify and explain before proposing, and never silently change semantics. I am proposing none of these.

**11.1 There is no revoke, and the UI cannot pretend otherwise.** The only canonical writes are `submit_designation`, `submit_continuation_surface`, `submit_grouping`. A continuation surface cannot be cleared, and cannot be reduced below two subjects because a valid declaration requires ≥2. Arity dispatch (§3) softens this — one mark becomes a legal designation rather than a rejection — but it does not create a path back to "I am not continuing anything." **Consequence for the design:** the UI must never offer "clear," and commitment must feel consequential rather than casual. **I am not proposing a revoke observation.** If you want one, it is an RFC, not a UI change.

**11.2 Designation is global; a continuation surface is per-workspace.** The merged control unifies their presentation while their scope stays asymmetric. §3.4 proposes making the asymmetry *visible* as Home's hero rather than hiding it. If that coupling is unacceptable, the merge still works and Home loses its hero. **This is a decision for you, not a change I would make unilaterally.**

**11.3 BE-01 must be fixed before Phase 2.** `handle_designation` → `new_with_designated` passes `continuation_surface: None`, so a designation erases a declared surface. Under arity dispatch a user reducing three marks to one would silently destroy their declaration. This is a backend fix and I will not make it. It gates Phase 2.

**11.4 Preflight staleness is a contract property, not a bug.** A dot is a statement about the recent past; the engine independently recomputes at press time. I propose copy that tells the truth (§7.6) rather than any change to preflight. Noted only so the copy change is not mistaken for a workaround.

**11.5 Moving work off the UI thread touches call sites, not contracts.** Phase 5 calls existing derivation and preflight APIs from a worker. No signature, schema, or contract changes. If a type turns out to lack `Send`/`Sync`, I will flag it rather than change it.

**11.6 `context_chain` and `blockers` are permanently empty today — and that is the contract, not a gap.** RFC-0010 §"Interaction with IS-0021" fixes the order in which they may ever be populated: freeze the evidence schema, implement the producer, amend IS-0021 §25.4/§25.5, then implement derivation — and states that "until then, IS-0021 §25.5 continues to produce explicit insufficiency." Three of those four steps are unstarted. I am therefore designing no UI for either field and deleting the branch that pretends otherwise. If they are ever populated, that is a new design conversation — which is the correct outcome, since a UI built speculatively around empty fields is a UI built on a guess.

**11.7 The explanation copy has a prescribed shape, and I am following it.** RFC-0010 §Explainability contrasts a permitted explanation ("the work continues with B because the frozen derivation establishes it from canonical evidence") with a forbidden one ("Evo thinks you'll probably work on B next"). The existing string *"You marked this as the work to continue, so Evo didn't rank or guess"* is the user-facing form of the permitted shape, which is a large part of why I preserve it verbatim (§8). Any future copy in this region must keep that shape: state the ground, never the guess.
